# Перевірка production-середовища та безплатних лімітів

Актуальність перевірки: **16 вересня 2026 року**.

Цей документ описує кешування фотоархіву, фактичні production-вимірювання та приблизне навантаження, за якого сайт може наблизитися до лімітів безплатних планів Vercel, Neon і Cloudinary.

У документі навмисно немає значень змінних середовища, ключів API, OAuth-секретів або рядка підключення до бази даних.

## 1. Як проходять запити

### Дані фотоархіву

```text
Браузер
  → клієнтський кеш TanStack Query
  → Next.js / Vercel
  → серверний Data Cache
  → Neon Postgres лише при cache miss
```

### Зображення

```text
Браузер
  → Vercel Next Image Optimization
  → Vercel CDN cache
  → трансформоване зображення Cloudinary
  → Cloudinary CDN / storage лише при cache miss
```

Браузер не звертається до Neon для отримання файлів фотографій. Neon зберігає лише метадані: назву, опис, дату, gallery ID, Cloudinary URL та технічні поля.

## 2. Кешування даних фотоархіву

### Серверний кеш

`getPhotos()` кешує кожну окрему комбінацію параметрів:

- галерея;
- рік;
- місяць;
- cursor сторінки;
- кількість записів.

Час серверного кешування — **1 година**.

Однакова вибірка протягом цієї години зазвичай не виконує повторний SQL-запит до Neon. Кеш спільний для користувачів, тому сто відвідувачів з однаковим фільтром не означають сто запитів до бази.

Сторінки фотоархіву та галерей також використовують ISR з `revalidate = 3600`.

Під час створення, редагування або видалення фотографії застосунок:

- скидає кеш відповідної галереї;
- скидає кеш архіву;
- виконує revalidation відповідних сторінок;
- оновлює активний клієнтський список.

### Клієнтський кеш

Кожна комбінація фільтрів фотоархіву зберігається у TanStack Query:

- `staleTime`: 1 година;
- `gcTime`: 1 година;
- автоматичний refetch при поверненні у вкладку вимкнений;
- автоматичний refetch після відновлення мережі вимкнений.

Наприклад, перехід `Уся школа → Шкільне життя → інша сторінка → Фотоархів` у межах однієї вкладки може використати вже отримані дані.

Клієнтський кеш очищається після повного перезавантаження, закриття вкладки, використання іншого браузера або режиму інкогніто. Навіть тоді серверний кеш Vercel може не допустити звернення до Neon.

### Пагінація

- mobile: до 10 записів за один запит;
- desktop: до 50 записів за один запит;
- наступна порція завантажується лише під час прокручування до кінця поточної.

## 3. Кешування фотографій

Для картки галереї Cloudinary створює варіант:

```text
c_limit,w_480,q_auto,f_auto,fl_strip_profile
```

Для модального перегляду використовується варіант до `2400px`.

Після цього `next/image` створює файл відповідного розміру і формату під конкретний браузер та екран. Тому для однієї фотографії можуть існувати окремі кешовані варіанти для:

- різної ширини екрана;
- різного device pixel ratio;
- JPEG, WebP або AVIF;
- картки галереї;
- великого перегляду.

Оригінал завантажується безпосередньо з Cloudinary лише після натискання кнопки завантаження.

### Перевірені production-заголовки

Повторний запит однієї мініатюри через `next/image` показав:

```text
Перший запит:  x-vercel-cache: MISS
Другий запит:  x-vercel-cache: HIT
Cache-Control: public, max-age=2592000, must-revalidate
```

`2592000` секунд — це **30 днів**.

Прямий повторний запит до Cloudinary також повернув CDN `hit`. Це підтверджує роботу обох рівнів кешу.

Production-сторінка `/archive` під час перевірки повертала:

```text
x-vercel-cache: HIT
x-nextjs-prerender: 1
```

Тобто сторінка віддавалася з Vercel без повторного формування через Neon.

### Чому на одному комп'ютері видно повторні завантаження

Найчастіші причини:

- у Chrome DevTools увімкнено `Disable cache`;
- виконано `Empty Cache and Hard Reload`;
- відкрито інкогніто або новий браузерний профіль;
- пристрій потребує іншої ширини зображення;
- браузер підтримує інший формат;
- локальний browser cache був очищений системою.

Прапорець `Disable cache` працює, поки DevTools відкритий. Для коректної перевірки його потрібно зняти. У колонці `Size` повторний ресурс може бути позначений як `memory cache` або `disk cache`.

Навіть коли браузер повторює HTTP-запит, `x-vercel-cache: HIT` означає, що Vercel віддав готовий файл і не звертався повторно до Cloudinary.

## 4. Фактичний стан на дату перевірки

### Фото і база

| Показник | Значення |
| --- | ---: |
| Кількість фотографій | 10 |
| Сумарний розмір оригіналів | приблизно 13,3 MB |
| Середній розмір оригіналу | приблизно 1,33 MB |
| Розмір Neon-бази | приблизно 8,5 MB |

### Production-трафік

Вимірювання виконувалися у чистому headless-браузері з desktop viewport.

| Дія | Передано даних |
| --- | ---: |
| Перше відкриття головної | приблизно 0,80 MB |
| Перше відкриття «Шкільного життя» | приблизно 0,91 MB |
| Перше відкриття сторінки класу | приблизно 0,90 MB |
| Перше відкриття фотоархіву | приблизно 0,87 MB |
| Чотири різні сторінки в одному сеансі | приблизно 2,6 MB |
| Відкриття одного великого фото | приблизно 0,15 MB |
| Завантаження середнього оригіналу | приблизно 1,33 MB |

Це орієнтовні значення. Реальний трафік залежить від пристрою, браузера, viewport, DPR, стану кешу та дій користувача.

## 5. Vercel Hobby

Актуальні основні ліміти:

- 100 GB Fast Data Transfer;
- 1 000 000 Function Invocations;
- 4 години Active CPU;
- для актуальної моделі Image Optimization:
  - 5 000 image transformations;
  - 300 000 image cache read units;
  - 100 000 image cache write units.

Документація:

- [Vercel limits](https://vercel.com/docs/limits)
- [Image Optimization limits and pricing](https://vercel.com/docs/image-optimization/limits-and-pricing)
- [Vercel plans](https://vercel.com/docs/plans)

У частині загальної документації ще може відображатися старий показник `1 000 Source Images`. Фактичну модель конкретного акаунта потрібно дивитися у `Vercel → Usage → Image Optimization`.

### Оцінка за кількістю відвідувачів

Розрахунок використовує приблизно 2,6 MB на сеанс із чотирьох різних сторінок.

| Активність | Сеансів за 30 днів | Орієнтовний трафік |
| --- | ---: | ---: |
| 100 відвідувачів на день | 3 000 | 7,8 GB |
| 500 відвідувачів на день | 15 000 | 39 GB |
| 1 000 відвідувачів на день | 30 000 | 78 GB |
| 1 300 відвідувачів на день | 39 000 | 101 GB |

При звичайному перегляді поріг 100 GB відповідає приблизно **38–40 тисячам таких сеансів на місяць**, або **1 250–1 350 відвідувачам щодня**.

Якщо кожен відвідувач додатково відкриває 10 великих фотографій:

```text
2,6 MB + 10 × 0,15 MB ≈ 4,1 MB за сеанс
```

У такому сценарії 100 GB відповідають приблизно **24–25 тисячам сеансів на місяць**, або **800–830 відвідувачам щодня**.

Image transformations не збільшуються при кожному перегляді вже готового варіанта. Вони збільшуються переважно при першому cache miss для нового поєднання зображення, ширини, якості й формату. З поточними 10 фотографіями цей ліміт має великий запас.

Vercel попереджає про наближення до лімітів. Hobby-проєкт може бути призупинений після вичерпання включеного usage.

## 6. Neon Free

Актуальні основні ліміти:

- 0,5 GB storage;
- 5 GB public network transfer на місяць;
- 100 CU-годин на місяць;
- автоматичний scale-to-zero після 5 хвилин без активності.

Документація:

- [Neon pricing](https://neon.com/pricing)
- [Neon network transfer](https://neon.com/docs/introduction/network-transfer)
- [Neon scale to zero](https://neon.com/docs/introduction/scale-to-zero)

### Storage

```text
8,5 MB / 500 MB ≈ 1,7%
```

Вільно приблизно 98,3%. Файли фотографій у Neon не зберігаються, тому основне зростання створюють метадані, розклади, користувачі, audit logs та error logs.

### Network transfer

Одна невідкешована порція з 50 записів орієнтовно може передати 10–25 KB із Neon:

```text
5 GB / 25 KB ≈ 200 000 невідкешованих вибірок
```

Завдяки спільному серверному кешу фактична допустима кількість відвідувань значно більша.

### Compute

Якщо мінімальний compute дорівнює `0.25 CU`:

```text
100 CU-hours / 0.25 CU = 400 активних годин на місяць
400 / 30 ≈ 13,3 активних години на день
```

Окремий запит після тривалого простою може залишати compute активним приблизно 5 хвилин. Теоретична межа за повністю розділених у часі пробуджень:

```text
400 годин / 5 хвилин ≈ 4 800 пробуджень на місяць
≈ 160 на день
```

Це песимістичний сценарій. Запити, які приходять протягом одного активного проміжку, не створюють окремі п'ятихвилинні блоки, а кешовані сторінки можуть взагалі не звертатися до бази.

Перевищення 5 GB public network transfer на Free plan може призупинити compute до наступного циклу або переходу на платний план.

## 7. Cloudinary Free

Free plan має 25 кредитів у ковзному вікні 30 днів:

```text
1 кредит = 1 000 transformations
або 1 GB managed storage
або 1 GB image bandwidth
```

Storage, bandwidth і transformations додаються між собою.

Документація:

- [Cloudinary billing and plans](https://cloudinary.com/documentation/billing_and_plans)
- [Cloudinary usage data](https://cloudinary.com/documentation/programmable_media_asset_usage_data)
- [Cloudinary transformations](https://cloudinary.com/documentation/image_transformations)

Поточні оригінали використовують приблизно:

```text
13,3 MB ≈ 0,013 кредиту storage
```

Звичайні перегляди йдуть через Vercel Image Optimization. Після прогрівання кешу Cloudinary не обслуговує кожен браузерний перегляд окремо.

### Завантаження оригіналів

Кнопка завантаження звертається безпосередньо до Cloudinary. За поточного середнього розміру:

```text
25 GB / 1,33 MB ≈ 18 800 завантажень за 30 днів
≈ 625 завантажень щодня
```

З урахуванням storage і transformations практичний орієнтир — **17–18 тисяч завантажень оригіналів за 30 днів**.

Cloudinary застосовує soft limit: приблизно біля 90% надсилає попередження, а перевищення 100% не означає миттєве вимкнення. Якщо перевищення зберігається після повторних повідомлень, акаунт можуть відключити, включно з upload і delivery.

## 8. Практичний прогноз

| Активність | Оцінка |
| --- | --- |
| 50–100 відвідувачів на день | Дуже великий запас усіх трьох планів |
| 300–500 відвідувачів на день | Поточна архітектура має працювати стабільно |
| 800–1 000 відвідувачів на день | Потрібно регулярно контролювати Vercel |
| 1 300+ відвідувачів на день | Ризик досягнення 100 GB Vercel |
| 600+ завантажень оригіналів щодня | Ризик для Cloudinary bandwidth |
| Постійні невідкешовані DB-запити протягом дня | Ризик для Neon compute |

Для нормальної активності невеликої школи поточних безплатних планів має вистачати зі значним запасом. Найчутливішим загальним обмеженням є Vercel Fast Data Transfer. Cloudinary стає ризиком переважно при масовому завантаженні оригіналів, а Neon — при безперервних невідкешованих запитах або неконтрольованому накопиченні логів.

## 9. Регулярна перевірка

Рекомендовано раз на тиждень або після помітного зростання відвідуваності перевіряти:

### Vercel

`Project → Usage`

- Fast Data Transfer;
- Function Invocations;
- Active CPU;
- Image Transformations;
- Image Cache Reads;
- Image Cache Writes.

### Neon

`Project → Usage` або сторінку організації з usage-показниками.

- Compute / CU-hours;
- Storage;
- Public network transfer;
- чи compute переходить у scale-to-zero.

### Cloudinary

`Programmable Media → Usage` або `Console Settings → Billing`.

- загальні credits;
- storage;
- bandwidth;
- transformations.

Практичні пороги для ручної перевірки:

- до 50% — нормальний стан;
- 50–75% — перевірити темп росту;
- 75–90% — запланувати оптимізацію або зміну плану;
- 90% і більше — реагувати одразу на попередження сервісу.

## 10. Важливі примітки до вимірювань

- Ліміти сервісів можуть змінюватися. Перед важливими рішеннями потрібно звірятися з офіційними сторінками та dashboard конкретного акаунта.
- Трафік залежить від браузера, пристрою, DPR, форматів, кешу і поведінки користувача.
- Боти, сканери або цілеспрямоване масове завантаження можуть витратити ліміти швидше, ніж звичайні користувачі.
- Hard reload та `Disable cache` у DevTools показують сценарій нового користувача, а не звичайний повторний перегляд.
- Значення цього документа є оцінкою, а dashboard кожного провайдера залишається остаточним джерелом фактичного usage.
