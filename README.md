# Йосипівська початкова школа

Next.js App Router + React + TypeScript, SCSS Modules, Auth.js/Google OAuth, Neon PostgreSQL/Drizzle, Cloudinary та WeatherAPI.com. Специфікація — `AGENTS.md`; фінальні правила розділів 29 і 35 визначають ролі `admin`, `class_1`…`class_4` та редагування лише метаданих фото.

## Локальний запуск

```sh
nvm use
npm ci
npm run dev
```

Відкрийте http://localhost:3000. Потрібен Node.js ≥20.19; `.nvmrc` задає 20.19.6. Без `DATABASE_URL` доступні всі публічні сторінки з явно позначеними демо-фотографіями та розкладом. Зміни й підроблений вхід у цьому режимі недоступні. Дані не зберігаються в localStorage або файлах сервера.

## Підключення сервісів

1. Якщо `.env.local` ще немає, скопіюйте `.env.example` у `.env.local` та заповніть значення локально. Наявний файл не перезаписуйте: у ньому вже можуть бути робочі ключі й підключення. Не публікуйте цей файл.
2. Створіть Neon Postgres.

Set up this Neon project in the current working directory.

    1. `npm i -g neon@latest && neon login`
    2. `neon skills -y`
    3. `neon mcp -y`
    4. `neon link --project-id dawn-river-12148537 --branch production -y`
    5. `neon config init`
    6. Update `neon.ts`:

    ```ts
    import { defineConfig } from "@neon/config/v1";

    export default defineConfig({});
    ```

    7. `neon deploy`



 `DATABASE_URL` — pooled-підключення сайту. `DATABASE_URL_UNPOOLED` — пряме підключення для міграцій і службових команд Drizzle; якщо його немає, використовується `DATABASE_URL`. Застосуйте `npm run db:migrate`.
3. Для розробки запустіть `npm run db:seed`: створюються рівно чотири класи, шість часових слотів, початковий поточний тиждень, 160 спільних демо-записів фотографій і два користувачі з ТЗ. Повторний seed не перезаписує існуючі ролі або розклади. Записи користувачів стають видимими в адмін-кабінеті після справжнього Google-входу.
4. Налаштуйте Google OAuth web application: callback `http://localhost:3000/api/auth/callback/google`, для production — `https://ваш-домен/api/auth/callback/google`. Заповніть `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`; створіть `AUTH_SECRET` командою `openssl rand -base64 32`.
5. У Cloudinary заповніть `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`. Дозволений домен Next Image обмежений вашим cloud name. Після зміни змінних перезапустіть або перебудуйте застосунок.
6. `SITE_URL` — канонічна адреса production для metadata, sitemap та robots. У локальному режимі використовується localhost.

## Початкове налаштування production

Використовуйте окрему чисту Neon database і виконайте міграції. Development seed навмисно заборонений із `NODE_ENV=production`. Спочатку увійдіть власним Google-акаунтом, потім у захищеному терміналі з підключенням до цієї БД виконайте:

```bash
npm run db:bootstrap -- your-verified-email@example.com
```

Команда додає чотири класи, часові слоти та роль адміністратора лише користувачу, який уже входив через Google. Вона не додає демонстраційний контент і не перезаписує наявні дані. Призначення прав записується в аудит.

Подальші права призначайте через `/admin`. Для останнього адміністратора є окреме підтвердження зняття прав; власник БД може відновити доступ цією ж командою. Офіційні адреси соцмереж додайте до `SOCIAL_LINKS` .

## Розклад, галереї та кеш

- Весь час обчислюється для Europe/Kyiv. Публічний розклад показує поточний календарний тиждень; у суботу/неділю редактор відкриває наступний. Старі тижні зберігаються. Оновлення дати в уже відкритій вкладці — кожні 30 секунд, даних розкладу — щохвилини.
- Інформаційні сторінки — SSG. Класи — ISR 60 секунд, галереї й архів — ISR 3600 секунд. Зміни використовують точкові `updateTag` / `revalidatePath`. `/admin` та API сесії — request-time, оскільки залежать від поточного користувача.
- Архів читає таблицю `photos`, фільтрується через URL за роком, місяцем і галереєю. Курсор — `creationDate + id`, порядок стабільний. Початковий набір 10 фото, наступні набори 10/50 залежно від ширини контейнера; рядки віртуалізовані.
- Редактор фото змінює назву, опис і дату. Заміна зображення — лише видалення та створення. Підтримані JPEG, PNG, WebP, HEIC/HEIF. Браузер зменшує великі JPEG/PNG/WebP; для HEIC/HEIF понад 5 МБ пропонує вибрати менший файл, як дозволено ТЗ. Сервер перевіряє розмір, MIME та формат, Cloudinary декодує HEIF. Видаються лише оптимізовані варіанти без EXIF/GPS.

## Узгоджене видалення й технічне обслуговування

Видалення фото спочатку записує запит у `asset_cleanup_jobs`, потім видаляє Cloudinary-файл і транзакційно запис/метадані та job. Якщо сервіс відмовляє, користувач отримує помилку, а durable job залишається для повторення. Невдале створення після успішного upload намагається прибрати новий asset і фіксує cleanup failure окремо.

Помилки зберігаються в Neon `error_logs`, успішні зміни — в `audit_logs`. У Neon SQL Editor останні помилки завантаження фото можна переглянути так:

```sql
SELECT created_at, user_email, location, error_code
FROM error_logs
WHERE location LIKE 'photo.create%'
ORDER BY created_at DESC
LIMIT 20;
```

`photo.create.upload` позначає помилку на етапі Cloudinary, `photo.create.database` — під час запису метаданих, `HTTP_401` — відмову провайдера в авторизації. Сирі повідомлення Cloudinary, ключі та вміст фото в логах не зберігаються. Якщо сама БД недоступна, коротке повідомлення потрапляє в stderr серверного процесу.

```sh
npm run db:cleanup
```

Запускайте цю команду щодня в захищеному середовищі з production credentials (локальний scheduler або наявний CI). Вона обробляє до 100 завдань старших години за запуск, не конфліктуючи з активним upload; повторюйте для великої черги. Після завершення фонового видалення публічний ISR-кеш оновиться протягом години. Помилки зберігаються 90 днів, аудит — 365 днів. У логах немає токенів, ключів або сирих повідомлень провайдерів. Якщо сама БД недоступна, безпечна класифікація помилки потрапляє в платформний stderr.

## Перевірки

```sh
npm run lint
npm run typecheck
npm test
npm run build
npx playwright install chromium firefox webkit
npm run test:e2e
```

Інтеграційні тести виконують реальні Drizzle-запити й міграцію на PGlite (PostgreSQL у тестовому процесі). Auth boundary та Cloudinary в цих тестах підмінені; у застосунку тестових bypass немає. Перевіряються дозволи, серверні мутації, унікальність розкладу, відкат транзакцій, cleanup та спільність архівних даних.

Playwright запускає окремий production-сервер на порту 3100 та перевіряє публічні сценарії в Chromium, Firefox і WebKit на mobile/tablet, lightbox, focus, нескінченне завантаження, URL-фільтри та відсутність горизонтального overflow. Погода підмінена фікстурою тільки в E2E. Справжні Google OAuth / Neon / Cloudinary потребують налаштованих зовнішніх акаунтів; їхнє наскрізне живе проходження не імітується.

## Візуальні оновлення з TASKS.md

Навігація закріплюється біля верхнього краю після прокручування шапки. Перехід між сторінками повертає прокручування точно на початок; посилання з якорями зберігають перехід до потрібного блоку. SVG-іконки замінюють текстові стрілки, шеврон меню класів плавно повертається. Чотири фони в `public/images/backgrounds/` змінюються кожні 20 секунд із трисекундним переходом і поступово зникають унизу фонової області. Розмір цієї області залежить лише від екрана (`max(100svh, 56.25vw)`), тому масштаб і позиція зображення однакові на всіх сторінках. За reduced motion показується статичний фон. Промпти та походження — `docs/BACKGROUNDS.md`.

## Автооновлення погоди

Віджет запитує прогноз щогодини, зокрема у фоновій вкладці, та перевіряє застарілі дані після повернення у вкладку чи відновлення мережі. Якщо браузер повністю приспав вкладку, оновлення відбудеться після її пробудження. HTTP-відповідь `/api/weather` не кешується браузером/CDN; спільний серверний кеш має окремий ключ для кожної години, тому перший запит нової години очікує свіжий прогноз. Тест `tests/e2e/weather.spec.ts` перевіряє це без реального очікування години та без перезавантаження сторінки.

Погода використовує серверну змінну `WEATHERAPI_KEY` у `.env.local` (на хостингу додайте її окремо). Запит — за точними координатами школи з українськими описами. Запитуються 7 днів; якщо тариф повертає менше, віджет показує тільки доступні дні. Ключ не додається до браузерної відповіді.

### База знань

Розділ `/knowledge` містить статичні матеріали попереднього шкільного сайту.
Групи, підпункти та ознака `hidden` розміщені в `src/lib/knowledge.ts`.
Текст і назви вкладень редагуються в `src/content/knowledge.ts`, профілі педагогів —
у `src/content/teachers.ts`. Оригінали документів лежать у `public/knowledge`.
PDF мають локальні зображення сторінок для перегляду на всіх пристроях;
DOCX — текстове представлення з таблицями та посилання на оригінал.
При додаванні нового PDF потрібно підготувати зображення всіх його сторінок і
внести їх у `pages` відповідного матеріалу. Приховані підпункти не включаються
до навігації, статичних маршрутів та sitemap. Історія школи й педагоги
відображаються на `/history#school-history` та `/school-life#teachers`.
